# Video scraping — design

Status 2026-10-06: first live run done (see "First run"). Numbers marked
*measured* were measured; everything else is a design choice to be checked by
the calibration set (see "Calibration").

The record format is a contract and lives in `CLAUDE.md` ("REQUIRED data
format for VIDEOS"). This file is the reasoning behind the pipeline.

## Why video, and what we want from it

The dataset is street-level flood imagery for geolocalization. Dashcam and
phone video of driving or walking through a flooded street is structurally
the same geometry as Street View (camera at person/vehicle height, road in
frame, facades passing). News photos have low yield on that geometry
(about 32% under the strict prompt; see `CLAUDE.md` "Dataset direction").

**Scope (owner's decision, 2026-10-05):**

- Collect videos that are **relevant to flooding**. That is the bar.
- **Coordinates are not required.** A video without them is kept, with
  `lat`/`lon` = `null`. It is never dropped for lacking them.
- **New York is a label, not a filter.** `in_ny` / `in_nyc` are `true`,
  `false` or `null` (unknown). Searches are aimed at NY so most results are
  NY, but nothing outside NY is discarded.

## Pipeline

```
search.list  (plan: event windows -> geo circles -> flood term x NY place)
    |  every answer appended + flushed to scrape_data/youtube_searches.jsonl
videos.list  (new ids + re-check of every existing video, 1 unit / 50 ids)
    |
labels       video_signals.py: flood_text_score, flood_event_date, in_ny/in_nyc
    |        coordinates (when the uploader set them) vs the Census NY boundary
thumbnails   i.ytimg cover + hq1/hq2/hq3, fetched + fingerprinted
    |        (shared data/image_hashes.json); undecodable ones and in-video
    |        repeats dropped
data/youtube_videos.json             merged, atomic, newest first
data/youtube_videos_meta_data.json   regenerated by the same run
    |
(next) VLM over thumbnails -> flood_visual          [not built yet]
```

Files:

| file | role |
|---|---|
| `scraping/video_scraping/youtube_scrape.py` | the scraper (steps 1-5 in its docstring) |
| `scraping/video_scraping/video_signals.py` | flood text score, NY labels, event matching. Source-agnostic, so a second video source reuses it |
| `make_youtube_metadata.py` | the metadata snapshot; `refresh()` is called by the scraper |
| `scrape_data/youtube_searches.jsonl` | search cache. Like `mycoast_pages.jsonl` it is a **cache, not unmerged work**: deleting it only costs quota |

## YouTube Data API v3 facts that shape the design

**Quota.** The free quota is 10,000 units a day. `search.list` costs **100**
units, so about 100 searches a day, 50 results per page, and in practice no
more than about 500 results per query however far you page. `videos.list`
costs **1 unit per 50 ids**. Search is the scarce resource; enrichment is
nearly free. Consequences:

- Every search answer is persisted the moment it arrives. A crash or the
  quota running out mid-run loses nothing already paid for.
- **The search cache is the bookmark between days.** Paging is
  breadth-first: page 1 of every search, then page 2 of every search, and so
  on, down to `--pages` (default 10, about YouTube's ~500-result limit). Page
  N+1 uses the `next_page_token` stored on cached page N. A run that hits the
  budget stops wherever it is, and the next day's run of the **same command**
  skips everything cached and carries on. Each level of the 74-search plan
  costs about 7,400 units, so it is about one level per day.
- **Walk, then re-walk, forever** (owner's design, 2026-10-07; see
  `CLAUDE.md` in this folder for the discussion behind it). Once no
  unfetched page remains, each run re-fetches saved pages **oldest first**,
  keeping relevance order. 740 pages at about 93 a day means every page is
  refreshed about every 8 days. Page tokens are positions, not snapshots
  (`CDIQAA` decodes to "from result 50", identical for every search), so a
  re-walked page is that slot of the current ranking. New uploads that rank
  into a query's top ~500 are caught on the next visit to the page they
  landed on. A re-walked page that gains a token (the search grew) becomes
  walk work for the next run. Pages already fetched in the current run are
  never re-fetched in it. A page token YouTube rejects (`invalidPageToken`)
  is cached as an empty final page; the re-walk retries it in turn.
- **Videos.** `data/youtube_videos.json` is keyed by `video_id`, so a video
  found again by a new search is merged into its existing row, not
  duplicated. Its `queries` gain the new search label.
- **Reserve for `videos.list`.** Searches stop early enough to leave units
  for re-checking every stored video (`ceil(N/50)`) plus fetching every new
  id the searches could return (1 unit per search page). Otherwise a
  full-budget run would find videos it cannot afford to fetch that day. With
  2,761 stored videos and the default 9,500-unit budget, that allows 93
  search pages a day.
- **Runs daily from cron** at 03:30 Eastern, after the midnight-Pacific quota
  reset. See `CLAUDE.md` Commands.
- Within a level, the plan is ordered most-specific first (event windows,
  then geo, then the term x place grid).
- Re-checking every stored video costs `ceil(N/50)` units. For 10,000 videos
  that is 200 units, so it runs by default.

**What `search.list` can filter.** There is no "is this a flood" filter.

| parameter | used | caveat |
|---|---|---|
| `q` | yes; NOT operator (`-minecraft -roblox -fortnite`) pushes the worst false positives server-side, OR (pipe) in event queries | operators are best-effort, not strict boolean |
| `publishedAfter` / `publishedBefore` | event windows: event day + 7 days | upload date, not recording date |
| `location` + `locationRadius` | 6 circles over NY | only matches videos whose uploader set a location: a small minority |
| `regionCode` | **not used** | it is a market setting, not "filmed in" |
| `relevanceLanguage=en` | yes | a bias, not a filter |
| `videoEmbeddable=true`, `type=video` | yes | |
| `videoCategoryId` | **not used** | one category per call; categories are scored after the fact instead |
| `videoDuration`, `videoLicense` | not yet | candidates once yield is measured (short/medium for dashcam; `creativeCommon` for redistributable pixels) |

**The search plan** (`search_plan()`, 74 searches = 7,400 units, fits one day):

1. **Event windows**: 8 major NY floods (Irene, Lee, Sandy, Henri, Ida,
   2023 Hudson Valley, 2023-09-29 NYC, 2024 Long Island), each searched for
   uploads in the 7 days after. The date restriction is what makes a broad
   query like "flood New York" precise.
2. **Geo circles**: NYC, Long Island, Hudson Valley, Capital Region, Central
   NY, Western NY.
3. **Term x place grid**: 5 flood phrasings x 12 NY places.

`--query` replaces the plan for ad-hoc runs; `--plan` prints it with its cost.

**API key.** The key is read from `$YOUTUBE_API_KEY`, or else from
`YOUTUBE_API_KEY` in `.env`. It is sent as the `X-goog-api-key` header, never
as a URL parameter. A `requests` error message includes the URL, so a key in
the query string would end up in logs (*measured*: the bogus-key test error
message contains no key).

**Terms of Service: no video bytes.** Downloading video (yt-dlp etc.) is
against YouTube's ToS. The licensing argument for news photos applies too: we
store URLs and metadata, never pixels. The pipeline therefore sees a video
only through its metadata and YouTube's own thumbnails.

## Thumbnails: what is available without downloading

`i.ytimg.com/vi/<id>/` serves, publicly and permanently, with no key:

| file | what |
|---|---|
| `maxresdefault.jpg` / `sddefault.jpg` / `hqdefault.jpg` / `mqdefault.jpg` | the cover in 4 sizes. The uploader may have chosen a custom cover, which is often text-heavy clickbait |
| `hq1.jpg`, `hq2.jpg`, `hq3.jpg` (480x360), `1.jpg`..`3.jpg` (120x90) | **automatic frames** at about 25 / 50 / 75 % of the video. Not chosen by the uploader, so they are the honest view of the content |

*Measured 2026-10-05* on two videos:

- All of `hq1`-`hq3` and `1`-`3` returned 200.
- `maxresdefault` and `sddefault` returned **404 with an `image/jpeg` grey
  placeholder** on an old video. Checking the content type alone would have
  accepted it.
- `hq2.jpg` was **byte-identical to `hqdefault.jpg`** when the uploader set
  no custom cover.

So the cover's URL comes from the API's `snippet.thumbnails`, which lists
`maxres` only when it exists. Every thumbnail is fetched and decoded
(`dedupe.fetch_digests`, shared cache). Only thumbnails that decode are kept,
which is the same displayability proof as `image_sha256` for images, and the
404 placeholder fails `raise_for_status`. Exact repeats inside one video are
dropped. Repeats across videos (re-uploads) are reported, not dropped.
Cached fetch failures for thumbnails are retried on every run, because a
transient failure would otherwise drop a thumbnail permanently.

Four frames per video is thin, but it is what the ToS allows. It is enough
for a video-level "is flooding visible" vote. It is not enough to pick the
best street-view frame from a dashcam clip. That limitation is accepted for now.

## Deciding "is this about flooding": three signals

The signals are recorded independently. **None is a filter**, the same
invariant as the news verifiers.

### Signal 1: text (`score_flood_text`, `flood_text_score` + `flood_text_hits`)

It reuses `verify_text.py`'s `STRONG` / `WEAK` / `METAPHOR`, so news and video
share one flood vocabulary, and adds:

- **Video-specific strong phrases**: `flooded street/road/subway/basement`,
  `driving through flood`, `water rising`, `cars stuck/floating`,
  `#flood*`, `#nycflood`.
- **Weak (street-context) terms**: `dashcam`, `storm drain`, `manhole`,
  `underpass`, `hydroplaning`, `nor'easter`, `heavy rain`. These support a
  strong hit; they never substitute for one.
- **Hard negatives (score forced to 0)**: games and their flood mechanics
  (Minecraft, Roblox, Fortnite, Cities: Skylines, "flood escape", "natural
  disaster survival", GTA, gameplay); CG and toy floods (water simulation,
  Blender, Houdini, LEGO dam breaks); film and music (official trailer or
  video, lyrics, full movie); `flood fill`, `flood light`, Noah's ark; flood
  insurance and real-estate tours. **Matched in title and tags only**; in the
  description the same terms are a soft negative. In the first run,
  description matches zeroed 32 of 44 videos, nearly all genuine flood news
  (PIX11 "Families clean up from Staten Island flooding", whose description
  mentioned insurance; broker channels with "real estate" boilerplate). After
  the change, 13 videos are zeroed.
- **Soft negatives (−0.15 each, capped at −0.45)**: `compilation`,
  `top N`, `most shocking`. These are usually real floods, but stitched from
  other people's clips with no reliable place or date.
- **Metaphor (−0.30 each)**: "a flood of memories" has to cancel the
  title hit it causes.
- **Penalised categories**: Film & Animation (1), Music (10), Gaming (20) and
  Entertainment (24) count as a soft negative. News & Politics (25), People &
  Blogs (22) and Autos & Vehicles (2, where dashcam clips land) are neutral.

**Weights.**

- **Title**: +0.45 for any strong hit (uploaders name the event there).
- **Tags**: +0.15.
- **Description**: up to +0.20, for up to 5 strong hits, counted *after*
  stripping boilerplate lines (links, handles, subscribe, sponsor and
  licensing copy, which often repeat across a whole channel).
- **Weak terms**: up to +0.10.
- **Event named in the title and in tags or description**: +0.10.

`flood_text_relevant` = `flood_text_score >= FLOOD_TEXT_THRESHOLD`
(`video_signals.py`; 0.3, owner's choice 2026-10-06). It is recomputed on
every run, so changing the threshold needs only `--no-search`, about 1 unit
per 50 videos. Calibration should still check it.

*Measured on hand-made titles* (title only, no tags or description; a
smoke test, not an evaluation):

| title (category) | score | in_ny / in_nyc |
|---|---|---|
| "Flooded street in Hollis, Queens NY after heavy rain" (22) | 0.49 | true / true |
| "Driving through flood on the BQE" (2) | 0.45 | true / true |
| "Flash flooding in Houston, Texas" (25) | 0.45 | false / false |
| "Rochester flooding" (25, channel News10NBC) | 0.45 | true / false |
| "A flood of memories: my trip" (22) | 0.15 | null / null |
| "Top 10 most shocking flood videos compilation" (24) | 0 | null / null |
| "Minecraft flood escape map!!" (20) | 0 | null / null |

With tags `["flood", "nyc"]` and a flood description, the Hollis video
scores 0.70-0.74.

**Limits.** Signal 1 says the video is ABOUT a flood. It does not say
flooding is VISIBLE, and certainly not that the camera is at street level.
Captions failed that test for news ("a caption saying 'street' describes the
EVENT, not the camera"), and titles fail it in the same way. Non-English
titles score about 0 and are kept with that score. The vocabulary is English
only.

### Signal 2: known flood event (`flood_event_date`)

This is the latest known NY flood day on, or up to 3 days before, the
recording date (else the upload date). Known flood days are:

- the hand list in `video_signals.NY_FLOOD_EVENTS`, and
- every day with at least 5 MyCoast NY reports: 96 days of 535 reported days
  (*measured*). At 3 reports per day the count is 193, mostly routine
  king-tide reporting, so 5 is the cut.

A matching date corroborates both "flood" and "NY". A missing one means
little, because most uploads are not tied to a big event.

### Signal 3: visual (`flood_visual`, NOT BUILT YET)

The local Qwen model over the kept thumbnails, asking two questions per
frame:

1. **Flood prompt (new)**: is standing or moving floodwater visible on a
   road, sidewalk, yard or building entrance? Answer no for rain without
   standing water, wet pavement, rivers within their banks, and maps or
   graphics.
2. The existing **street-view `PROMPT`**, unchanged.

The video-level flood answer is yes when at least 2 of the auto-frames say
yes. Agreement across frames removes most one-off model errors, and the
custom cover is excluded from the vote because it is chosen to attract
clicks. Thinking stays OFF (see `CLAUDE.md` Invariants). The scraper already
preserves `flood_visual` across re-scrapes, so the verifier can write it into
the same file.

## Deciding "is this New York" (`label_new_york`)

Every signal that fires is appended to `ny_basis`. The precedence is:

1. **Coordinates** (`coordinates`). If the uploader set a location, it is
   tested against the Census TIGER NY boundary and the NYC borough boundary
   (`gis_scrape.Regions`). This decides `in_ny` and `in_nyc` outright. The
   boundaries are fetched only if some video has coordinates.
2. **Place names** (`gazetteer`). Two tiers:
   - **Standalone**: names that are NY wherever they appear, such as Brooklyn,
     Bronx, Staten Island, Manhattan, Far Rockaway, Howard Beach, Canarsie,
     BQE, FDR Drive, Major Deegan, Belt Parkway, Long Island, Hamptons,
     Catskills, Finger Lakes and the LIRR. A negative lookahead drops
     "Manhattan Beach" (CA), "Manhattan, KS" and "Brooklyn Park, MN".
   - **Marker-only**: names that are also common words, another state's town,
     or a country, such as Queens, Jamaica, Flushing, Rochester, Buffalo,
     Albany and Elmhurst, plus every `place` in `data/mycoast.json` (232 NY
     localities, many far more famous elsewhere: Mexico, Jordan, Memphis,
     Geneva, Cairo). These count only when a NY marker (`NY` in capitals,
     `N.Y.`, `New York`, `NYC`), a standalone name, or a NY-only channel is
     also present. They are matched case-sensitively, in Title case or all
     capitals.
3. **Channel** (`channel`).
   - NY-only outlets (NY1, News 12 Long Island/Brooklyn/Bronx/Westchester/
     Hudson Valley, and the Buffalo, Rochester, Syracuse and Albany stations)
     mean `in_ny` is true.
   - Tri-state NYC stations (PIX11, ABC7NY, NBC New York, CBS New York,
     FOX 5) also cover NJ and CT, so they mean `in_ny` is true only if the
     text names nowhere else.
4. **Elsewhere**. If the text names another US state, a big non-NY city, a
   `, XX` state abbreviation, or a common flood-news country, and nothing NY
   was found, then `in_ny` is false. Otherwise it is null.
5. **Event date** (`event_date`). Recorded as corroboration; it never decides
   anything alone.

`in_nyc` is true when coordinates fall in the city, or the text names an NYC
place or says NYC / New York City. It is false when the video is NY but only
non-NYC NY places are named. Otherwise it is null.

**Deliberately conservative.** "Queens street flooding" with no other cue
stays null. A wrong `true` would poison a geolocalization evaluation set,
while a null only costs recall.

**Not done (yet).** `channels.list` (`snippet.country`, channel description)
is weak evidence (people film where they travel) and was left out. Reading
NYC-specific cues in frames (MTA signage, yellow cabs, street-sign style)
with the VLM is a possible tie-breaker later.

## Coordinates

Coordinates are optional, but kept when they exist:

- `location_basis = "api"`: `recordingDetails.location`, set by the uploader.
  This is rare.
- `location_basis = "overlay_ocr"` (reserved, not built): many dashcams burn
  GPS coordinates and a timestamp into the frame. OCR on the auto-frames
  could recover per-frame ground truth, the most valuable thing YouTube could
  give a geolocalization project. The scraper already refuses to overwrite an
  `overlay_ocr` location on re-scrape.

A place name is never turned into coordinates. Geocoding "Hollis, Queens"
gives a neighbourhood centroid, which is not where the camera was.

## Playability, deletion and re-scrapes

- **New videos** that are not public, not embeddable, age-restricted, or an
  upcoming premiere or stream are not written, and the run log counts them.
  The review site could not play them.
- **Existing videos** are re-checked every run. A video that has since been
  deleted, made private or blocked keeps its row with `available = false`, so
  the labels spent on it are not lost.
- **On a re-scrape**, a record is rebuilt from fresh API data. `queries` is
  unioned with the old value, and `flood_visual` and an `overlay_ocr`
  location are carried over.

## Calibration (before trusting any threshold)

1. Run the plan once. Hand-label about 150 videos for three things: shows
   flooding, street-level, and NY. Sample across score bands, not just the
   top.
2. Measure:
   - precision and recall of `flood_text_score` at several thresholds;
   - precision of `in_ny = true` per basis;
   - how often `in_ny` is null for videos that are in fact NY (the recall
     cost of being conservative);
   - which queries and plan stages pay (each record's `queries`).
3. Build signal 3 and measure it against the same labels.

## First run (2026-10-06, *measured*)

The full plan was 74 searches, plus `videos.list` and thumbnails, spending
7,442 quota units.

- **Videos**: 2,074 kept; 1 was not playable and was skipped. Upload dates
  run from 2006-08 to 2026-10-06. Median duration is 80 s; 74 videos are over
  20 minutes.
- **Thumbnails**: 8,279 kept (11 did not decode, 6 repeated within a video),
  so `thumbnails_without_digest` = 0. 29 are shared across videos
  (re-uploads).
- **`flood_text_score`** (after the hard-negative fix): 1,587 videos
  relevant at the 0.3 threshold (1,522 at 0.4), 13 hard negatives.
- **Searches**: 3,654 results gave 2,075 unique videos (43% overlap between
  searches). 68 of the 74 searches have more pages. The stages contributed
  400 (event), 261 (geo) and 1,414 (grid) new videos. So page 1 is far from
  everything; deeper pages are what the following days' runs fetch.
- **`in_ny`**: 1,731 true, 182 false, 161 null. Of the 182 false, 100 come
  from coordinates (the geo circles spill into NJ and CT, and the boundary
  test catches that). The other 82 come from text naming elsewhere; "New
  Jersey" accounts for 81 term hits.
- **`in_nyc`**: 957 true.
- **Coordinates**: 343 videos have them, 264 of those found by the geo
  circles. That is far more than expected. Uploaders of local flood clips set
  a location more often than YouTube at large.
- **`flood_event_date`** set: 859.

**Observed in a sample** (by title, not frames):

- The 0.6+ band is almost all real NY flood news or footage.
- Upstate place names without a NY marker stay null by design. For example,
  "Thunderstorms cause flooding in parts of Amherst, Buffalo" from WIVB stays
  null; WIVB is in the NY-only channel list, but its channel title is
  "WIVBTV", which the pattern misses.
- Some genuine flood clips score low because their wording is unusual
  ("CARS HAD TO BE PULLED OUT OF WATER", 0.32).
- `score 0` without a negative is mostly non-flood water content (water main
  breaks, jet boats, lake views).

These are reasons to calibrate before choosing a threshold. They are not
fixed yet.

## Open questions

- Should `videoDuration=short|medium` be added to cut news shows and
  livestreams, at the risk of losing long dashcam drives?
- Should the plan be widened beyond NY? The same code works; only
  `PLACE_TERMS`, `GEO_CIRCLES` and the event list are NY-specific.
- Should `videoLicense=creativeCommon` be searched separately to build a
  redistributable subset?
- Dashcam GPS overlay OCR: worth a probe on a handful of real dashcam videos
  once the first run exists.
- Other video sources (Vimeo, TikTok, Facebook) only through official APIs,
  reusing `video_signals.py` and the same record contract.
